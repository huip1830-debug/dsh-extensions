# 派发纪律成本重设计：二维判级与验证职责唯一

> 日期：2026-10-27
> 触发问题：派发纪律让主控与子代理的消耗都增大、执行时间变长，是否为正常量级？
> 数据基础：两日全量实测——`session-8634bdc8-416d-481a-902e-28c50f51884b`（oa-01「事项督办」，10-26，主会话+10 子会话完整解压）与 10-27 全天样本（8 主会话 + 20 子会话，跨 oa-01 / ocr-01 / scale-03）。
> 结论先行：**消耗量级正常（缓存命中 ~96%），但存在三处结构性成本倒挂**。根因不是某条规则写错，而是纪律只有「权责安全」一个维度，缺「成本配比」维度。修复为二维判级制，0.5.0 落地其文本部分（方案一）。

### 1.2 样本二：10-27 全天（8 主会话 + 20 子会话）

- 主会话合计：fresh 70.1 万 / cache 1581 万 / out 15 万。
- 子会话合计：fresh 116.5 万 / cache 2176 万 / out 34.4 万；**首步固定成本合计 31 万 fresh**（oa-01 每个子代理首步 17~25K，scale-03 为 6.7~15K——固定成本随项目上下文体积变化）。
- 全天 5 个有派发的会话**无一使用勘察批次**，全部直接派实现——对模式清晰的任务，实践已自发跳过勘察。
- 主控上下文膨胀实测：子代理报告注入每会话仅 1K~32K 字符（零头）；主控 fresh 最高的会话（ocr `session-4afbd4a8`，21.8 万 fresh）只派了 1 个子代理、自己 `pwsh×23`——**主控自己收长命令输出才是主控 fresh 的第一来源**。

### 1.3 三处成本倒挂（本文要修的全部问题）

1. **评审重复跑验证命令**。10-27 的评审/复审子代理实测工具序列：`pwsh×24~33` + `read×13~18` + `grep×8~16`，在重跑主控已复跑过的构建/测试。6 个评审合计 ~41 万 fresh + 840 万 cache；「文案改名」一例中评审成本（7.1 min / 86K fresh / 59 次工具调用）**超过被评审的 3 个实现批次之和**（各 ≤2.2 min / 共 16K out）。「randomUUID 修复」评审 42 步 / 9.5 min / 64.7K out。
2. **微批次启动成本倒挂**。「文案改名」3 个实现批次的启动成本各 17K fresh，产出各只有 4~7K——启动成本是工作量的 2~4 倍。
3. **主控长输出治理缺位**。纪律已有「跑长命令收输出默认派给子代理」，但开工判级时没有强制检查点，执行靠自觉。

## 2. 根因诊断

现行纪律的所有条款回答三个问题：谁能写（白名单互斥）、谁能提交（派发方）、谁说了算（复跑+独立评审+裁决归派发方）。这些是原始目标，全部保留。

它从未回答第四个问题：**仪式的规格应该多大**。三个倒挂症状是同一个缺失的三个表现——验证的执行者与判定者没分家（症状 1）、批次粒度没有成本门槛（症状 2）、规模判断没有显式检查点（症状 3）。

## 3. 重设计：二维判级制

### 3.1 新决策树

```
任务 → 二维判级（写进任务清单）:
        风险轴: 任一批次命中并行写/契约面 → 整个需求 gated（原逻辑不变）
        规模轴: 单批预估 <10min 或纯模式克隆且模式已在主控上下文 → 微批
  ├ 微批   → 按 §3.3 分流（主控直做 或 合并单代理）→ 复跑 + diff 自查留证，免独立评审
  ├ 标准批 → 合并批次（宁少勿多）→ 复跑 → 评审（若派）为案头核对
  └ 重批   → [勘察仅当主控写不出现状] → 契约冻结 → 互斥并行 → 复跑 → 全规格评审
  全程: 判级升级通道（§3.5）+ 度量闭环（§3.6）
```

### 3.2 验证职责唯一（修症状 1）

- **执行性验证**（跑命令、看退出码）：只归派发方。集成命令由主控复跑，输出全文（含退出码）是评审派发词的必备输入。
- **语义性核对**（逐条 PASS|FAIL + 文件:行号）：归评审。合法动作只有 read/grep 对照需求原文/契约/diff；**禁止重跑构建/测试/集成命令**。
- 一条验证，全系统只付一次钱。文本约束进 0.5.0 规则 3；沙箱层（只读 label 禁 pwsh 执行）留作 profile 角色表的后续跟进项，不在 0.5.0 范围。

### 3.3 固定成本门槛与微批分流（修症状 2）

派发一个子代理的固定成本 ≈ 首步上下文（6.7~25K fresh，随项目而异）+ 派发词（~1-2K out）+ 串行墙钟。**批次预期工作量盖不住固定成本时不许拆批**；并行从默认动作改为有价购买。

微批去向按序判定，第一条命中即停：

| # | 条件 | 去向 | 依据 |
|---|---|---|---|
| ① | 验证需跑构建/长命令或输出大 | 派出 | 主控收大输出直接抬高贵模型 fresh（§1.2 末条实证） |
| ② | 改动 >2 文件或同模式改写 ≥3 处 | 派出 | W 随文件数线性涨，主控直做的价差成本 W×(k−1) 迅速超过启动成本 |
| ③ | 本会话后续仍有已规划派发批次 | 派出 | 上下文污染税：工具结果滞留主控上下文，被后续每步 cache 重读，与剩余步数成正比 |
| ④ | 均不命中（≤2 文件、验证短平快、会话收尾） | 主控直做 | 此时启动成本 > 直做全部增量成本；须先读原文并在回复给出改动与验证证据 |
| ⑤ | 判不准 | 派出 | 错误不对称：错派代价有上限（一次启动成本），错收无上限（价差 + 污染税随 W 涨） |

同需求的多个微批合并为**一个**子代理：白名单取并集、内部串行。

**与「不写死数字」的关系**：既有设计拒绝数字门槛（README「为什么不写死数字」），针对的是**验收边界**（白名单由「一条集成命令能验完」界定、清单由「一条=一决策/一批」界定）——数字不解决验收负担，该立场不变。微批分流的阈值是**成本路由**的校准初值：判错只影响成本不影响正确性（⑤兜底），且由度量闭环（§3.6）负责修正。两类门槛的性质不同，不冲突。

### 3.4 勘察触发条件显式化

勘察批次的唯一触发条件：**主控现有上下文写不出含「文件:行号 + 相关代码 + 结论 + 不确定项」的现状**。主控刚读过相关模块、或任务是已知模式克隆时免派勘察，现状直接引用已读证据。10-27 全天样本证明实践已自发如此，条文化是为了消除临场自由裁量。

### 3.5 判级升级通道（新护栏）

执行中发现改动面超出判级预估——触及白名单外文件、新增契约面、工作量显著超预估——必须停手重新判级。这是微批免评审的主要风险对冲：判级判错时，流程有内生的升级出口，与「不得自行扩大范围」同级。

### 3.6 度量闭环

纪律退化的发现不能依赖事后手工解压 zstd。三个指标，数据源全部既有：

| 指标 | 告警线 | 数据源 |
|---|---|---|
| 评审/实现成本比 | >1 | 会话 jsonl 的 per-agent usage |
| 启动成本/批次产出比 | >1 | 同上（首步 fresh vs 输出） |
| 微批返工率 | 趋势上升 | 插件 observation rows（`dispatch/runs/*.jsonl`）+ decision log |

超标时的处置：收窄微批豁免范围（④ 收紧到单文件）、上调拆批门槛；框架不动。采集脚本（解压 session jsonl 聚合 usage）留作后续工具项，0.5.0 只落指标定义。

## 4. 旧优化清单逐项裁决（10-27 全天数据验证）

|---|---|---|---|
| 1 | 按规模分级、免勘察批次 | 真实但低频；实践已吸收 | 10-27 五个派发会话零勘察 |
| 2 | 评审输入收窄 | **真实且被低估，升级为 §3.2** | 评审 pwsh×24~33 实锤；评审成本多次超过实现批次 |
| 3 | 派发词模板化 | 伪需求，偏负向 | 当日派发词已短至 874~2955 字；模板化鼓励敷衍「现状」，损害子代理成功率 |

## 5. 对任务完成度的影响：净正向

**正向机制**：
1. 信息保真度上升——微批主控直做时需求原文与问答澄清都在主控上下文，无派发词转述损耗。
2. 评审质量不降反升——禁跑命令后评审的步数预算全部用于语义核对（需求遗漏、边界条件）。
3. 强模型用在刀刃上——微批由主控直做，完成质量 ≥ 子代理；勘察豁免时用主控一手证据，无二手转述。

**负向风险与护栏**：

| 风险 | 护栏 |
|---|---|
| 微批免独立评审 → 主控自查确认偏误 | 仅限低风险轴；diff 自查留证可事后抽查；微批返工率进度量卡，超标即收窄豁免 |
| 合并批次 → 单代理上下文变长、出错面变大 | 白名单互斥与内部串行不变；NEEDS_CONTEXT 停报机制不变；批次上限受子代理上下文容量约束 |
| 判级判错（微批做成一半变大改） | 判级升级通道（§3.5），与「不得自行扩大范围」同级 |

净结论：削减的全部是重复付费环节（重复跑命令、重复启动、重复转述），没有削减任何独立判断环节；重批场景的判断链（冻结契约→互斥→复跑→独立评审→裁决归派发方）一道不少。

## 6. 不动的红线

提交权归派发方；验收复跑并留存退出码；契约面派发前冻结；gated 判级不可按子代理切分绕过；评审裁决归派发方、评审不得改文件；白名单逐条列名、以一条集成命令为界；验收两层（窄验证归因 + 集成命令验集成状态）。

## 7. 落地路线

- **0.5.0（本次，方案一）**：纪律文本压缩改写进 `lib/config.mjs`（DEFAULT_RULES / DEFAULT_FOOTER），承载 §3.2~§3.5 全部规则。实测净增量 +520 字（1299 → 1819 字符，≈+700 tokens），按 10-27 的 770 步/天折算约 +5 万 fresh 等价/天，对实测可节省项（症状 1+2 合计每天数十万 fresh + 数百万 cache）ROI 超 10:1。机制代码零改动；`node test.mjs` 67/67 通过（两处文本措辞按既有断言口径微调：footer 避用「白名单」字样以保住「自定义规则整体替换默认文本」的探针，规则 6 保留连续子串「拆批方案或一行不派发理由」）。
- **方案二（暂缓，触发式启动）**：详版规程（成本推导、示例反例、阈值校准记录）经插件既有 steer 通道做条件注入。触发条件：度量卡显示返工率归因于规则理解偏差。skill 拆分方案已撤回——skills 为独立仓库（chanjet-docs 等），拆分引入跨仓库维护与版本同步成本；条件注入在同插件内即可闭环，无需第二仓库。
- **部署**（按 README 固定顺序）：提交推送 → `dsh plugin --profile desktop update dispatch-protocol` → 完全退出并重启 DSH → 台账记一笔。注意 README「已知坑」：update 前必须完全退出 DSH 并确认无遗留 robocopy/pnpm 进程。

## 8. 未决与校准项

1. 主/子模型价格比 k 与缓存折价率：从计费后台取实值后代入 §3.3 的不等式复核分流阈值（>2 文件 / ≥3 处 / <10 min 为初值）。
2. 只读评审的沙箱层禁跑命令：需改 profile 角色表（`cordis.patch.yml` 的 roles 段），与 0.5.0 文本约束配套，单独一轮做。
3. 度量采集脚本：会话 jsonl 解压聚合（本次分析用的方法）固化成脚本，定期出指标卡。
4. 观察期 2 周：重点看微批返工率与判级准确性，决定是否收紧分流④。
