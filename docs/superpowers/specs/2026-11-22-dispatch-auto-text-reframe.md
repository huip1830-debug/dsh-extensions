# dispatch-protocol 0.19.0 — `auto` 提级提示重框架：中性开场 + 正面示例

- 状态：**契约冻结**（2026-11-22，用户在会话中逐项裁决：接受文案重框架；拒绝加观测信号——「检查点已被验证几乎没有作用」；拒绝需求文本关键词触发——「文本判断不稳定」）
- 触发问题（2026-11-22）：「派发纪律，目前设定在 auto 时，很少有机会模型会自动升级到 full，是什么原因呢？」
- 版本：`0.18.0` → **`0.19.0`**
- 非目标：不改四档语义；不改 `dispatch_upgrade_full` 的可见性与 execute 契约；不加任何 auto 档观测/日志/提醒机制；不引入关键词或文件数触发器。

## 1. 诊断（维持 0.16.0 spec §3 的「模型漏问」风险判断，补上归因）

`AUTO_TEXT`（0.16.0 版）很少触发升级，是四层因素叠加：

1. **措辞偏向不问**：首句「本项目默认不启用派发纪律」把基线框成 off；「哪怕文件不少、看起来很大——不要问，直接做」是全文最强指令且为否定句；全文只有负例、零正例，「显著受益」无锚点；成本（轮次）具体、收益（四件事）抽象。
2. **判断时机无证据**：升级判断发生在需求入口、勘察之前，模型手里没有波及面信息；0.16.0 又刻意删掉硬触发条件，只剩无证据的主观判断，安全出口就是「直接做」。
3. **auto 无反馈回路**：守卫放行、检查点不投递、观测行不写，「该升没升」不留痕，漏问不可测量。
4. **模型先验**：请示 = 打断 + 多一个来回；「每需求最多问一次」把问定义成稀缺资源；升级单向不可逆，模型对重决策保守。

另需承认：部分「不升」是正确结果——full 的四个机制本质是多批次协作的协调成本，单文件小改诚实回答就是「不显著受益」。

## 2. 契约

### 2.1 `AUTO_TEXT` 重写（`lib/config.mjs`）

三处变更，其余逐字保留：

1. **首句中性化**：删「本项目默认不启用派发纪律」，改为「当前项目处于自动档：派发纪律不拦截、不提醒，是否升级到 full 由你在收到需求时判断」。陈述事实与责任归属，不预设结论。
2. **补正面示例**（场景式，非关键词）：三类典型应请示情形——契约面（schema/类型/接口/路由/权限/迁移）且多调用方随动；拆成多个并行/先后批次、需要独立评审与统一集成；用户明确要求过程纪律或验收可追溯。
3. **负例降调**：删「哪怕文件不少、看起来很大——不要问」，保留反向边界「单一模块内的小改、纯文案或配置调整、一次就能完成的修复，直接做、不必问」。

保留不动的要素：四件事清单、判断问句「会不会从上面四件事中的至少一件显著受益」、「每需求最多问一次」、被拒后不再问、工具名 `dispatch_upgrade_full` 逐字、dock/`/dispatch full` 兜底、子代理不评估。

### 2.2 明确不做的两件事（用户裁决）

- 不在 auto 档加任何观测/日志/提醒。检查点类机制已在 0.17.0 前后的真实会话中验证价值低，不以此为基础实现漏问测量。
- 不在提示段或代码里引入需求文本关键词触发（「提到『所有调用方』就请示」之类）。文本判断不稳定，误报比漏问更伤体验。

## 3. 兼容与风险

- **行为变化只有一处**：auto 项目根代理的提示段正文变化；无 marker 的项目下一节抱起生效（系统提示词每轮重组，无需重启；但 profile 插件更新本身仍需按 §5 重启）。
- **KV 缓存前缀**：README「已知坑」已说明提示词改动影响前缀复用，本次属有意为之。
- **风险：过度请示**。正例可能把请示率抬得过高。缓解是保留反向边界与「每需求最多问一次」；若实测噪声大，回退点是把三类正例压缩成一类（契约面）。
- **效果不可测是已接受的代价**：按 §2.2 用户裁决，不加观测就没有升级率数据，本次改动的效果只能靠使用体感判断。
