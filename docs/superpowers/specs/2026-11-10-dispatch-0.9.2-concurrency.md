## 1. 问题

| 冲突 | 现状 | 并行会话后果 |
|---|---|---|
| A 验证污染 | VerifyGate 只看本会话事件：`lastVerify` 之后本会话不脏就静默（`gates.mjs:401-403`）；别的会话的写入不可见 | 集成命令红/绿都可能混入别人的改动，模型按错误归因去修 |
| B 同文件覆盖 | 守卫只判断控制面，不判断文件是否被别的会话在你读之后改过（`write-policy.mjs:201-218`） | 同文件、barrel、lockfile 后写覆盖先写；读旧内容写新内容丢更新 |
| C 并发构建 | 没有构建租约；`gates.verify.commands` 只用于事后提醒（`gates.mjs:30`、`386`） | 两个全量构建/测试同时跑，`dist`、缓存、端口、测试库互相踩 |

0.9.1 的台账分文件只解决“状态文件谁写哪份”；它不解决代码、构建产物与验证窗口的并发。本版补的是这三类冲突的工具边界检测。

## 2. 契约（拟冻结；当前草案）

### 2.1 作用域

- **会话发现**：`ctx.agents.list()` 枚举 live 会话；`session.cwd ?? session.header.cwd` 取当前工作目录；`session.header.origin` 区分根/子代理；`session.header.parentSession` 建会话树。
- **自己 vs 别人**：同一根树（root 及其所有子代理）算“自己”；不同 root 树且 `cwd` 相同（大小写不敏感、反斜杠归一）算“别的会话”。
- **时间窗**：`concurrency.windowMs` 默认 `900000`（15 分钟）；`concurrency.buildLeaseMs` 默认 `1800000`（30 分钟）。只倒序扫描窗口内事件，遇到早于窗口的事件立即停止。
- **不做**：不新建共享文件/锁，不跨进程，不读磁盘上的会话日志。

### 2.2 数据

- 会话事件：`session.snapshotEvents()` 的 `tool/call`、`tool/result`，两者都带 `time`（毫秒）与 `data.turn`；`tool/call` 的 `data.name`、`data.arguments`（JSON 字符串）、`data.callId`。
- 守卫输入：`exec.agent`、`exec.name`、`exec.arguments`（已解析对象）。
- 读跟踪：`read` 工具调用成功与否都记录 `lastReadAt[root][normalizedPath] = now`；只认 `read` 工具，`pwsh` 里的 `Get-Content` 不算（§7）。
- 路径归一化：`\` → `/`、折叠 `.`/`..`、相对 `session.cwd` 解析、大小写不敏感；cwd 外的绝对路径按原样比较。口径与 `write-policy.mjs` 的 `normalizePath`/`toCwdRelative` 一致；`concurrency.mjs` 自带一份最小实现（与 `gates.mjs` 的 `readCommand`/`readPath` 同样处理），不修改 `write-policy.mjs`，但必须用同一组测试断言覆盖 `..`、绝对路径、盘符。

### 2.3 守卫判定顺序

对根代理：

1. `write/edit`：现有控制面授权（`evaluateWritePolicy`，不变）→ **stale write**（§2.4）→ **first-write notice**（§2.5）。
2. `pwsh`：**build lock**（§2.6）。

源码写入先经过控制面授权：没有 override 时由授权直接拒绝；授权放行的写入仍会经过 stale write，first-write notice 只对源码写入/派发触发。

对子代理：

- 只做 stale write（不拦 build，只记日志；first-write 由根代理的首次派发触发）。
- 现有“子代理直接放行”的控制面豁免不变（`plugin.mjs:224`），并发检查在豁免之前单独执行。

守卫整体仍包在 `try/catch` 里，任何异常按放行处理（fail-open，与 `plugin.mjs:254-257` 一致）；`concurrency.enabled === false` 时完全不进入并发判定。

### 2.4 stale write（B）

- `read` 更新 `lastReadAt[root][path]`。
- `write/edit` 时扫其他树、同 cwd 的 `write/edit` 事件；若存在 `time > lastReadAt`（从未读过时用 `root` 的会话开始时间 `session.createdAt ?? header.createdAt`；取不到开始时间时按 `0` 处理，宁可多拦一次），拒绝本次写入，`reason: 'stale-write'`。
- 拒绝文案（模型看到 `Error: <text>`，回合继续）：

  ```text
  [dispatch-protocol] 拦截：{tool} 要写 {file}，但会话 {session} 在 {time} 改过同一文件；你最后一次读它是 {readAt}（未读过时写「你还没读过」）。先重新 read 确认内容，再重试写入；若确实要覆盖对方的改动，先问用户。
  ```

- 重读后 `lastReadAt` 更新，下一次写入放行。控制面文件（`dispatch/state/<需求>.md`、`dispatch/ledger/<需求>.md`、`docs/superpowers/specs/*`）同样适用：两个会话改同一份台账也应先重读。
- 同一根树内的写入（父/子代理）不算冲突。
- 只覆盖 `write/edit`；`pwsh` 的 `Set-Content`/`Remove-Item` 等 shell 写不在此检查内（§7）。

### 2.5 first-write notice（worktree 逃生口）

- **触发**：根代理的第一次源码 `write/edit`（路径不在 `writePolicy.allowlist` 内），或第一次 `subagent`/`subagent_fork`/`workflow` 调用；同时满足：同 cwd 存在别的树，且对方在 `windowMs` 内有 `write/edit` 或存在未返回的构建命令。
- **只触发一次**：`notified[root] = true`；`mode: 'enforce'` 时拒绝本次调用（`decision: 'notified'`），模型重试同一调用即继续；`mode: 'shadow'` 时只记一行 `decision: 'observed'`，不拒绝、不投递。控制面写入不触发。
- 文案：

  ```text
  [dispatch-protocol] 并发提示：同一工作区还有会话 {session} 在活动（{activity}）。本批若写源码 + 跑全量构建，建议先 create_worktree；worktree 从 HEAD 开始，不带走未提交改动，dispatch/ 会另起一份，已有 shell 保持旧 cwd。若只是只读勘察/小改，重试同一调用即继续（本提示只出现一次）。
  ```

- `{activity}` 例：`12:03 写过 src/a.ts、package.json`；`12:05 起在跑 npm test`。
- 提示只拦一次：重试即继续共享工作区；不自动创建 worktree。

### 2.6 build lock（C）

- 根代理的 `pwsh` 命令命中 `concurrency.buildCommands`（默认复用 `gates.verify.commands`）时，扫其他树、同 cwd 的 `pwsh` 调用：命中 `buildCommands`、`time >= now - buildLeaseMs`、且没有对应 `tool/result`，视为并发构建（不要求同一条命令——不同构建同样会踩共享产物）。
- `mode: 'enforce'` 拒绝；`mode: 'shadow'` 只记日志。文案：

  ```text
  [dispatch-protocol] 拦截：会话 {session} 正在跑集成命令（{command}，{time} 开始，尚未返回）。等它结束再跑；或改跑窄命令；或问用户。
  ```

- 子代理的 `pwsh` 只记日志，不拒绝（窄命令允许并行）。
- 结果事件即释放；无结果的调用靠 `buildLeaseMs` 过期（进程崩溃/中断的兜底）。
- 命令匹配沿用现有 `matchesVerifyCommand` 的大小写不敏感子串口径；已知误报（`Get-Content tsconfig.json` 命中 `tsc`）由 `buildCommands` 配置收窄（§7）。

### 2.7 ContaminationGate（A）

- 位置：`Wait → Contamination → Verify → Contract → Review → Handoff`；同一回合仍只投递一条（`lastDeliveredTurn`，`plugin.mjs:465-467`）。
- 触发：本回合出现 `present` 或命中 `commitPattern` 的 `git commit/push`；取本会话最近一次集成命令（`pwsh` 命中 `gates.verify.commands`）的 `tool/call.time` 到收口之间，扫其他树、同 cwd 的 `write/edit` 与命中 `DEFAULT_PWSH_MUTATION_PATTERN` 的 `pwsh`；命中即返回 `{ lastVerify, foreign: [{ session, files }] }`。
- 本会话自己的子代理写入不算 foreign；没有集成命令可查时不触发。
- `files` 为空表示只命中 shell 变更，文案写「改动了工作区（shell）」；有路径时写具体文件。
- 文案：

  ```text
  [dispatch-protocol] 本次集成命令（{lastVerify}）开始之后，会话 {session} 在 {time} 写入了 {files}；本次验证结果不可归因。等空闲重跑，或迁 worktree 后重跑，不要据此改代码。
  ```

- 决定日志：`kind: 'gate'`、`gate: 'contamination'`、`decision: 'delivered'`、`lastVerify`、`foreign`。

### 2.8 配置

```yaml
concurrency:
  enabled: true
  mode: enforce          # enforce | shadow
  windowMs: 900000       # 15 分钟
  buildLeaseMs: 1800000  # 30 分钟
  buildCommands:         # 默认复用 gates.verify.commands
    - npm test
    - npm run build
    - dotnet test
    - jest
    - tsc
    - prisma migrate deploy
    - node test
  firstWriteNotice: true
  contamination: true
```

- 校验（加载期报错，前缀 `dispatch-protocol: concurrency.`）：`mode` 只能是 `enforce`/`shadow`；`windowMs`/`buildLeaseMs` 为正整数；`buildCommands` 为非空字符串数组；`firstWriteNotice`/`contamination` 为布尔值。
- 默认 `mode: 'enforce'`（build + stale write 都拦，first-write 软门拒绝一次）；`shadow` 只记日志，用于先观察误报，first-write 也只记 `observed`、不拒绝。
- `firstWriteNotice: false` 关闭软门；`contamination: false` 关闭收尾 gate。

### 2.9 决定日志

共用现有 `log`（`%TEMP%\dispatch-protocol-decisions.jsonl`）。新增：

```json
{"time":"...","session":"...","turn":null,"kind":"concurrency","decision":"denied|observed|notified","reason":"stale-write|build|first-write","otherSession":"...","files":["..."],"command":"...","mode":"enforce|shadow"}
```

- `notified` 是 first-write 软门；`observed` 是 shadow 下本应拒绝的判定；`denied` 是 enforce 下的实际拦截。
- ContaminationGate 仍走 `kind: 'gate'`，`gate: 'contamination'`。

## 5. 风险与已知限制

1. **只覆盖 live 会话**：已关闭/重启的会话看不到；它们不再并发，但留下的脏文件仍在工作区。跨 DSH 进程（多个 app 实例）也不可见；桌面版单进程是主场景。
2. **只覆盖同 cwd**：不同 worktree 的 cwd 不同，视为已隔离；端口/DB 仍共享，本版不处理。
3. **只覆盖 `write/edit`**：`pwsh` 的 `Set-Content`/`Remove-Item` 不在 stale write 内；first-write 提示也不覆盖 shell 首次写。
4. **构建命令是子串匹配**：`Get-Content tsconfig.json` 会命中 `tsc`；用 `concurrency.buildCommands` 收窄。误报成本是多一步等待。
5. **拦截多一步**：stale write 和 build lock 都会拒绝一次调用；模型重读/等待后重试。`shadow` 可先观察误报。
6. **worktree 逃生口不是自动的**：提示只给建议；worktree 从 HEAD 开始、不带未提交改动、`dispatch/` 会分叉、已有 shell 保留旧 cwd。用户要 worktree-first 需先解决共享状态目录（§7）。
7. **`ctx.agents` 是宿主单进程注册表**：若未来会话跨进程，本方案失效，需要退回文件登记表。
8. **first-write 提示有时点**：只反映第一次写入/派发时的并发状态；对方之后才开始活动不会补提示，靠 stale write / build lock 兜底。
9. **超长构建**：`buildLeaseMs` 默认 30 分钟；超过该时长的构建会被视为过期，另一个构建可能开始。长构建项目调大该值。

## 7. 决策记录：为什么是 guard-first，不是 worktree-first

worktree 在 A/B 的源码隔离上确实更彻底；不把它做成默认，是因为以下成本（见本 spec 与 2026-11-10 会话讨论）：

| 维度 | worktree | guard |
|---|---|---|
| A 验证污染 | 物理隔离，最干净 | 只能标记/串行 |
| B 同文件覆盖 | 物理隔离，冲突推迟到 merge | 写前拦 stale write，立即 |
| C 构建产物 | 每工作树独立 | 串行构建，不能并行 |
| 未提交改动 | 从 HEAD 开始，不带走 | 无要求 |
| `dispatch/` 台账 | 分叉，需共享目录 | 共享 |
| 依赖/环境 | 每工作树安装 | 无额外 |
| 合并/清理 | 延迟冲突 + 手动 | 无 |
| 端口/DB/缓存 | 仍共享 | 仍共享 |
| 可用性 | 实验 bundle 默认关 | 现有代码 |
| 成本 | 每会话启动成本 | 拦截多一步 |

结论：**guard-first + worktree 逃生口**。worktree 保留给大改动/反复冲突/需要并行全量构建的批次；若后续要把 worktree 作为默认，先解决三件事：`dispatch/` 共享目录、干净树（或明确 stash/commit）、端口/DB 命名空间。
