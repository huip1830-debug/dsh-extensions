### 做对了什么（这部分不要丢）

1. **需求先确认，再动代码。** T1 用 11 个问题澄清业务口径，T5–T7 分节确认设计，T8 才写设计文档并提交。这个顺序是对的。

5. **“契约先冻结”在 schema/API 文本层做到了。** T9 先改 schema、手写迁移、`migrate deploy`、提交 `b989e21`，再派 8 个写代理；这是正确的顺序。

## 2. 八个结构性缺口

### G1 完成门禁是自愿的，不是门禁

**事实**：`ledger.mjs check` 现有 14 行，最后一行 E-014；`gate E-014` exit 0。但 E-014 是“派发管线自身发布”，不是本次 scale-03 交付。本次会话没有任何 `ledger.mjs` / `gate` / `snapshot.mjs` 调用；本会话最终形成 5 个交付提交，T26 在无台账行时完成提交并声明完成，T27 关闭目标。

**设计哪条失效**：§7.1 的 `gate` 只在“有台账行”时生效；§8.2 明确“normal 不记账”；§11 风险 2 只写“台账靠人写，主控可能忘写”。这不是风险，是**门禁的可选性**：不写行 = 不触发 gate = 可以完成。

**后果**：“完成”仍然是模型自述。第三方拿到 git 和会话，无法用一条命令回答“这次交付凭什么算完成”。本次证据只存在于 T26/T27 的聊天文本和压缩摘要里。

> 公平地说：主控在字面上可以自称合规——每个子代理都是 normal，normal 不记账。问题正是设计允许这样切（见 G2）。

### G2 “批次”由执行者自己切，gated 判据可被切分绕过

**事实**：T9 同一回合派 8 个可写子代理，并改 schema/迁移——如果按“同一波次”作为一个批次，它同时命中“并行写”和“契约面”，应 gated；如果按“每个子代理”作为批次，8 个都是 normal。主控选了后者，逐批口头记“台账”，没有 `classReason`，没有 gated 评审，最后只有一次整体评审。

**设计哪条失效**：§3.1 把 batch 定义为“一次可独立验收的交付单元”，但没有定义“变更集（change set）”这一层；§3.3 的判据是**按 batch** 计算的。把同一需求切成 8 个 normal batch，就永远没有“同一批次内 ≥2 个可写子代理”。

**后果**：设计最想拦的场景（并行写 + 契约面）可以按定义合法地变成 normal。按设计判据它是 gated，按主控切分它不是——**两种读法给出相反结论，说明判据本身不可判定**。

### G3 并行只按文件互斥，没有按依赖分层

**事实**（五次可避免的往返/污染）：

- BE-3 要删 `purchaseOrderPullService`，发现白名单外的 `erp-pull.ts` 仍 import；T9→T10 追加授权。
- W-4 按契约删 Arrival 类型，发现 7 个白名单外文件会编译失败；T18 停报，T19 才批准方案 A。
- BE-8 按契约做“红冲重试/重新推送”前端，发现 BE-7 的后端端点尚未实现；T22→T24 空转。
- SPA-2/SPA-3 并行 import SPA-1 尚未创建完的模块；靠消息协调，最后靠集成构建兜底。
- 压缩摘要自述：“BE-1 反映并发期 tsc 曾被 BE-3 的 erp-push.ts 中途态污染 → 已恢复，复跑通过。”

**设计哪条失效**：规则 5 说“白名单必须按文件/模块互斥”“契约在派发前定死”“子代理不得并发跑共享产物的全量构建或测试”。但文件互斥不等于依赖互斥；契约文本冻结不等于消费者可调用；删除型改动需要**反向依赖闭包**，不是一份静态文件清单。

**后果**：并行波次里混着“提供者”和“消费者”，每个依赖缺口都要一次 NEEDS_CONTEXT 往返；共享工作区的 tsc 会读到别人写了一半的文件，产生假失败，破坏“失败可归因”。

### G4 评审是单体、晚到、且无法复跑

**事实**：T20 在三端集成全部通过后才派 1 个只读评审；范围 120 个文件 / 12 类条款，评审时长约 14 分钟。评审自己写明“集成结果未复跑，结论仅基于读代码/diff”；它抓出 F1–F10。评审发出完整结论后，会话里还有一条 “was stopped before it finished” 的结算记录；无论按哪种读法，都没有形成独立的评审文件。最终 T26 声明“12 类条款全部 PASS”，其中 F1 是派发方以“我授权过 DOC-1”覆盖了评审结论；F9/F10 作为“上线注意事项”保留，没有进入任何 gate 记录。

**设计哪条失效**：§4 阶段 4 / §7.1 要求“独立评审 + PASS|FAIL + 文件:行号”，但评审是只读的，不能复跑集成命令；所谓“独立证据”实际是**独立阅读**。§7.1 又写 `review.sandbox` 只记录、gate 不强制，“只读由角色策略保证”——本次角色策略并没有生效（见 G8）。

**后果**：评审容量与批次规模不匹配；一次 120 文件的静态评审不可能逐条验证 12 类契约。更严重的是，需求原文可以在冻结后被同一会话改写：DOC-1 把设计文档 §5.2 的“整码反查”改成“前缀解析”，评审将其判 FAIL，派发方事后判 PASS。裁决权本身没问题，**问题是需求变更没有独立记录、没有重新评审受影响切片**。

### G5 成本模型漏掉了真正的成本：墙钟、上下文、报告摄入、fan-out

**事实**：设计 §8 估算 normal 单批 10–14 步、gated 14–18 步、survey 3–5 步；实际 21 次派发、156 步、2h51。设计 §8.1 说 brief 600–1,800 字，§8.2 又说“≤800 字”（自相矛盾）；实际均长 2,094 字符。设计说子代理输出合同 ≤10 行；实际 48 条消息 168k 字符，含重复的 `send_message` + 收尾消息。T25 触发上下文压缩，最终完成依赖摘要。

**设计哪条失效**：§8 只数主控步骤，没有墙钟、上下文 token、报告摄入量、并发宽度、依赖往返、复审返工这些维度。8 路 fan-out 在共享工作区上并没有把墙钟压到 1/8，反而制造了中途态污染和逐子代理唤醒。

**后果**：成本红线不可度量、不可验收；“normal 不增加往返”在 8 个子代理各自回报时变成 8 次唤醒/验收回合。主控真正的瓶颈是上下文，不是步骤数。

### G6 提醒机制误判“只读”，且按子代理线性放大

**事实**：23 条决定中只有 2 条 delivered（W-2、BE-5），13 条 handled，6 条 read-only，2 条 nudge 均 suppressed。

- **W-4 误判**：第一次因 NEEDS_CONTEXT 结束时 0 次 edit，被 `ranReadOnly` 判为只读；随后恢复执行，第二轮做了 45 次 edit，但 `reported` 已置位，不会再提醒。
- **W-5 误判**：它用 `pwsh` 删除死代码文件，没有 `write`/`edit` 调用，被判为只读；实际有文件删除。
- **nudge 盲区**：只认 `write`/`edit`，`pwsh` 里的 `Remove-Item`/`Set-Content` 不计；本次 2 条 nudge 都是 handled，没有一条 delivered。
- **真正漏掉的不是子代理命令**：主控全程没写台账，没有任何提醒指向“这次变更集还没有 gate”。

**设计哪条失效**：§5 的 checkpoint 按“未验收子代理各一条”；`ranReadOnly` 只看工具名；`parentAlreadyHandled` 是父代理级、不是子代理级。§1.1 约束 C 说“同一事实至多一条”，但 checkpoint 数量随子代理数线性增长，最坏一个回合可投递 N 条（`drain` 对每个 delivered 都 `steer`）。

**后果**：删除型/恢复型子代理被静默；提醒瞄准的是“每个子代理的命令”，而不是“变更集是否可完成”；在 8 路 fan-out 下，提醒的噪声与遗漏同时存在。

### G7 证据活在会话里，压缩即丢失

**事实**：本次没有 `dispatch/runs` 产物、没有评审报告文件、没有 gate 输出文件；评审结论只在会话消息里。T25 压缩后，T26/T27 的完成声明建立在压缩摘要上。台账 `~/.dsh/dispatch-ledger.jsonl` 不在版本控制，E-014 之后没有本会话的行。

**设计哪条失效**：§3.4 说“证据唯一位置 = dispatch-ledger.md/jsonl”，但台账靠手写、且在版本控制外；§1.2 又明确“不做运行时拦截”，于是没有任何机制在写盘/完成时把证据落下来。

**后果**：压缩后无法从文件重建“谁做的、改了什么、凭什么算完成、没派发为什么”。本次最终回复写得很完整，但它是**叙述**，不是**可复跑的证据**。下一次会话无法验证它。

### G8 “只读角色”没有生效：命名约定不是机制

**事实**：desktop profile 的 `subagent-model-pin.roles` 只匹配 `Survey` / `Review` 前缀；本次 3 个勘察和 1 个评审的 description 是中文（“后端入口链代码勘察”“只读评审：对照设计逐条验收”），全部未命中。子会话事件显示 `sandbox/mode = danger-full-access`，不是 `read-only`。它们没有写文件，是因为 prompt 写了“禁止修改”，不是因为沙箱挡住了。

**设计哪条失效**：§2 说 `subagent-model-pin` 负责“勘察与评审子代理的只读约束”；§7.1 说 `review.sandbox` 只记录、“只读由角色策略保证”。真实使用里，角色策略依赖一个模型不知道的英文命名约定。

**后果**：“只读评审”不是独立证据的保证；勘察子代理理论上可以改基线，评审子代理理论上可以改被评审的代码。E-006 的正向证据不能推广到真实标签。

## 3. 全局重构：从“批次纪律”到“变更集账本”

不要在这套结构上继续加字段/加提醒。要换的是下面这些基本单位：

| 旧 | 新 | 为什么 |
|---|---|---|
| batch（执行者自切） | **change set → slice → task** | 需求/契约/验收的单位必须独立于“这次派了几个子代理” |
| 文件白名单互斥 | **依赖 DAG + 波次屏障** | 可并行 = 无编译/运行依赖 + 无共享产物，不只是文件不同 |
| 手写台账 | **自动证据清单（manifest）** | 完成证据不能靠人记得写 |
| 事后 gate | **完成转换门禁** | 在 `goal complete`/最终回复前检查，而不是“有行才查” |
| 单体评审 | **切片评审包 + 跨切片一致性评审** | 120 文件一次评审不可完成 |
| 步骤成本 | **墙钟/上下文/报告/fan-out 预算** | 真实瓶颈是上下文与延迟 |
| 每子代理 checkpoint | **每波次/切片一条完成状态提醒** | 提醒应指向“变更集能否完成”，不是“每个孩子的命令” |

### 3.1 变更集（ChangeSet）：唯一可验收单位

```
CS-xxx
├─ spec:        { path, sha256, frozenAt, approvedBy }
├─ contract:    { schemaHash, apiSurfaceHash, migrationHash }
├─ slices: [
│    { id, kind: contract|backend|web|wpf|docs,
│      deps: [sliceId], files: [...], 
│      verify: { cwd, cmd, expect } }
│  ]
├─ batches: [{ id, slice, agent, briefHash, files, status }]
├─ review:  { scope: [sliceId], verdict, findings[] }
└─ gate:    { specUnchanged, coverage, allSlicesVerified, reviewPass }
```

- `gated` 判据作用在 **change set** 上：并行写、契约面、迁移、删除跨模块、用户要求评审，任一命中就 gated；不能通过“把工作切成 8 个 normal batch”绕过。
- `normal` 也自动生成一行（成本由工具承担），只是不强制评审；这直接消掉“normal 不记账”带来的证据空洞。
- 一个 change set 可以有多个 commit，但只能有一个 `gate` 结果和一组验收命令；commit message 引用 `CS-xxx`。

### 3.2 并行：按依赖 DAG 分层，而不是按文件清单

推荐波次：

1. **契约层**：schema / migration / API 类型 / 接口签名，先提交或先落 stub；这一层不允许与消费者并行。
2. **提供者层**：后端端点、服务、共享工具；每层结束跑“接口可编译 + 契约测试”。
3. **消费者层**：后台页面、WPF、文档；消费者只能 import 已存在的模块。
4. **收口层**：文档同步、死代码清理、全量矩阵；文档不得早于代码冻结。

删除型改动必须先做**反向依赖闭包**（谁 import 它、谁挂载它、谁在测试里引用它），再定白名单；否则 W-4 的 7 个文件、BE-3 的 `erp-pull.ts` 会重复出现。共享 `bin/obj/dist` 的构建必须串行，或每个写波次用独立 worktree；“同一工作区 8 路并行 + 各自 tsc”是不可归因的。

### 3.3 证据：从“人写台账”到“工具落 manifest”

每个 change set 一个目录：

```
dispatch/runs/CS-xxx/
  manifest.json        # 命令、cwd、exit、日志 sha256、文件集、白名单差异、spec/contract hash
  diff.patch           # 冻结后的完整 diff
  review.md            # 评审逐条 PASS|FAIL + 文件:行号
  gate.json            # gate 机器结果
```

- `manifest.json` 由派发工具在每次 `subagent` / 验收命令后自动追加；主控只填 `classReason`/裁决这类判断字段。
- 文件集来自 `workspace/changes` 或 `git diff --name-status`，自动与白名单比对；不靠主控读 `git diff --stat`。
- 验收命令必须记录 `cwd`、完整命令、退出码、输出日志哈希；`by: dispatcher-rerun` 只是字段，gate 应校验**命令覆盖了哪些 slice 的文件**，而不是“至少有一条 integration”。
- 证据目录放进版本控制（或独立证据仓），交付 commit 里写 `CS-xxx` + `manifest.sha256`。这保留“真相源分离”，但让证据可复现。

### 3.4 门禁：在“完成转换”上，不在工具调用上

设计 §1.2 的“不做运行时拦截”应保留，但要区分：

- **不做**：拦截 `write`/`subagent` 等工具调用。
- **必须做**：在 `agent/turn-stopping` / `goal complete` / 最终回复前，检查当前 change set 是否有 `gate.json` 且通过；没有就阻止“完成”标记，或明确标为 `not done` + 需用户接受风险。

`gate` 至少校验：

1. `spec.sha256` 与冻结时一致（任何需求改写 → 新版本 + 重新评审）。
2. 每个 slice 的验收命令都跑过且 exit 0；覆盖该 slice 的全部变更文件。
3. 白名单差异为空；删除的文件在反向闭包里被解释。
4. gated 的每个 slice 有 `review.md` 的 PASS（或用户显式 `acceptedRisk` + 理由）。
5. commit 的文件集与 manifest 一致；`components.d.ts` 这类既有改动被排除。

**关键**：`gate` 必须由“完成动作”触发，而不是由“主控记得写台账”触发。目标关闭/最终回复是天然的完成转换点。

### 3.5 评审：切片包，不是 120 文件一次看

- 每个评审包 ≤ 20 个文件 / ≤ 3 个契约面；评审人只对包内 slice 负责。
- 评审输入 = 冻结 spec hash + 契约 hash + diff + 该 slice 的命令输出；评审人必须在独立 worktree 复跑该 slice 的命令（或采信 CI 的签名结果），否则只能算“阅读”，不能算“验证”。
- 跨 slice 再设一个集成评审，只看接口/类型/路由边界，不重复逐文件审。
- 需求冻结后，任何 spec 修改走 `spec-change` 记录（谁、为什么、影响哪些 slice），并重开受影响 slice 的评审；文档同步必须在代码冻结后，且不能改冻结正文（只能加 appendix/decision record）。

### 3.6 成本：按变更集设预算，按墙钟/上下文验收

建议先以本次会话为基线定预算（不是永久硬上限，超了要在 manifest 写理由）：

| 项 | 本次实际 | 建议起点 |
|---|---:|---:|
| brief | 均 2,094 字符 | ≤800 字（与设计 §8.2 对齐，删掉 §8.1 的 1,800） |
| 子代理报告 | 48 条 / 168k 字符 | 结构化 ≤ 2k 字符/子代理，禁止 send_message + 收尾重复 |
| fan-out | 8 路 | ≤4 路/波次；依赖链上的活不并行 |
| 全量矩阵 | 多次 | 每 change set 1 次（分 slice 窄验证 + 收口全量） |
| 评审 | 120 文件 / 1 人 | ≤20 文件/包，包数按 slice |
| 完成回合 | 逐子代理唤醒 | 每波次 1 次聚合唤醒 |

报告用固定 schema（`{status, files, commands:[{cmd,exit}], deviations, risks}`），主控只读 schema + diff，不读长文；这样能同时降上下文和降重复。

### 3.7 提醒：从“每个孩子”改成“每个波次/变更集”

- 每波次最多一条 checkpoint，内容是“本波次 N 个 slice 是否都验收/是否可 gate”，不是“每个子代理去读 diff”。
- `read-only` 判定改用**实际 workspace 变更**（`workspace/changes` / diff），不是工具名；`pwsh` 的删除/写入必须计入。
- `handled` 必须绑定到**该 slice 的验收证据**（跑过该 slice 的 verify 命令），不是“父代理在报告后调用过任意工具”。
- 子代理恢复（NEEDS_CONTEXT → continue）要重新武装检查点，按 `(childId, completionSegment)` 记账，不能一次 `reported` 永久关闭。
- nudge 保留为“0 派发 + 多文件写”的观测，但只在没有完成 gate 的回合提醒；它的终点应该是“去 gate”，不是“去复跑某个孩子的命令”。

### 3.8 运行时：完成状态机要和 goal 生命周期对齐

本次 T26 两次 `update_goal complete` 被拒（“complete and blocked require a direct human turn or the current goal round”），T27 才成功；代价是 2 次失败调用 + 1 个额外回合。设计 §4 阶段 6 把“完成”写成回复动作，但 DSH 里它是 goal 状态转换：

- 在 `gate` 通过前，不尝试 `complete`；把“完成就绪”作为 goal 的一个显式状态。
- 只有人类回合或 goal round 允许 complete；子代理回报触发的回合不应承诺“马上关闭目标”。
- 最终回复从 `manifest + gate.json` 生成，不从记忆/压缩摘要生成。

3. **依赖 DAG + 波次**：改派发模板：contract → provider → consumer → docs；删除型先跑反向闭包；每波次一个聚合唤醒。验收：同一波次不再出现“导入未创建模块/调用未实现端点”。

## 5. 不能丢的设计目标

重构不是把流程做轻，而是把“完成”做硬：

- **北极星不变**：可归因、可复现、可审计；评审独立于实现者自述。
- **成本仍是硬约束，不是方向**：贵模型做判断，机械活下沉；但预算要按墙钟/上下文/报告算，不能只数步骤。
- **不做工具调用拦截**：只在完成转换点做门禁，保留“运行时不拦截”的边界。
- **不新增插件**：能力放进现有 `dispatch-protocol` + `~/.dsh/dispatch/` 工具链。
- **真相源分离**：spec/contract/evidence/roles 各自唯一，不互相复述。
- **提醒只在证据缺失时出现**：nudge 仍是观测，不是门禁；但它的终点要指向 gate。
- **裁决权归派发方/用户**：`acceptedRisk` 必须显式、有理由、进 `gate.json`，不能靠事后一句“我授权过”。

一句话：**这次会话证明“评审”有价值，也证明“台账/门禁”没有接住完成。下一版的重点不是再加一条规则，而是让“完成”必须经过一个机器可验的变更集账本。**
