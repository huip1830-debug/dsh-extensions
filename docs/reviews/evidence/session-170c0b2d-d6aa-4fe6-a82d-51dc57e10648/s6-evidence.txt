**不是问题，这是设计的正常回退路径。** 插件的逻辑是：优先尝试 GPU 委托，构造或推理失败就自动回退 CPU（4 线程），并把**实际使用的后端**如实显示出来（评审已核过这两层回退：[FeatureExtractorPlugin.kt:201-232](mobile-app/plugins/feature-extractor/android/src/main/java/com/ziyou/ocrdemo/featureextractor/FeatureExtractorPlugin.kt#L201-L232)）。

对你的影响只有一个：**推理会比 GPU 慢**（MobileNetV3-Small float32 在 CPU 上单张约 200–500ms，GPU 上约 50–150ms）。验收时按实际后端如实记录即可——**如果 CPU 下 P50 仍 ≤500ms、P95 ≤1s，指标照样算通过**；反而"CPU 都达标"是更强的结论。

几个排查方向（如果你想确认为什么没用上 GPU）：

1. **你是不是在模拟器里跑？** 模拟器基本都没有可用的 GPU 委托，显示 CPU 属预期；
2. **真机的话**，看 logcat（tag：`FeatureExtractor`），GPU 委托初始化失败时会打印具体原因（常见：设备 GPU 驱动不兼容、模型含 GPU 不支持的算子）；
3. 这不阻塞周三 Demo——先按 CPU 后端测出指标；若 CPU 不达标而 GPU 达标，再决定是否值得深入 GPU 兼容问题，或换 int8 量化模型（CPU 上能再快 2–4 倍，只需替换 `model.tflite` 文件，代码零改动）。

一句话：**能识别、耗时达标就行，后端显示 CPU 只是告诉你"这次用的是 CPU"**。

## 需要准备（批量命中率测试）

这是出 Top-1/Top-5 指标的核心测试，准备工作有三步：

1. **先建档**：去"建档"页，用 ≥20 个实物各拍 3–5 张入库（SKU 名起得简短规范，后面要用）；
2. **准备测试照片**：对每个已建档的 SKU **再拍几张新照片**（不能 reuse 建档那几张，否则命中率虚高），文件名改成 `SKU名__序号.jpg` 格式——`__` 前面必须和建档时填的 SKU 名**完全一致**（这是判定对错的 ground truth），例如 `切割片4寸__01.jpg`、`切割片4寸__02.jpg`；
3. **把照片传到手机上**（微信/数据线/网盘均可，能进系统的文件选择器就行）。

然后点"批量命中率测试"→ 多选这些照片 → 自动逐张识别 → 输出 Top-1（≥70%）/ Top-5（≥90%）/ P50 / P95 四项判定 → **点"导出 JSON"留档**（真机会复制到剪贴板，粘贴到微信/备忘录发回来即可）。

  → 压测页：填充模拟库 → 千级比对计时（出规模扩展性指标）
